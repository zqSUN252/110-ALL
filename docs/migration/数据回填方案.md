## 4. 身份、关联与例外

### 4.1 收据号、无ID明细与增量

有旧稳定ID的实体以`source_system+dataset_namespace+旧ID`关联，snapshot哈希仅识别版本与导入批次。无ID的票件原始行以“快照+主单ID+sheet/原数组位置”定位和生成可重现UUID，保留原始行哈希；同一批次重跑不会新增。该定位不是跨快照永久身份。

新生产快照或重传改变行序时，按已存来源/稳定业务关系生成差异候选，唯一可证明的原行保持逻辑ID；同号多行、重复相同行或附件关联不明确时不得按数组序号硬续接付款/节点。对该父单采用冻结后的完整版本预览和人工确认，再切换有效版本；其他历史行保留作版本证据。不自动把917个收据号当917条完整仓储记录。

新仓储收据身份唯一只约束登记身份；货物行、原始箱单行、出库批次和到货批次允许同号多行。缺原生入库台账时，导入出运历史不能凭其货物行倒造“当前中国仓剩余库存”。

### 4.2 付款60条、水单UID与台账73条

先保留`legacy_slips`与`legacy_payment_ledger`两个来源表/暂存域，再做桥接。非空UID只在其真实来源范围唯一；55条缺UID按“数据集+账单旧ID+原数组位置+原行哈希”生成稳定来源ID，不能按金额日期产生UID。73行台账的sig/UID/billId/batch/审核时间和原水单共同用于提名关联，不能仅凭四要素自动合并。

一条有确定UID/批次及分配证据的付款可关联多账水单行和台账表现；重复表现不生成第二笔付款。没有确定依据的行保留独立证据并标待核，禁止直接以60+73相加创造已收。两笔合法同额同日同人交易必须都保留。

**跨快照永久身份：** 上述“账单ID+位置+原行哈希”只定位某快照的来源观察记录，不是永久付款ID。逻辑payment UUID首次经核实建立后单独保存，后续观察通过append-only来源映射指向它。跨快照只有稳定UID、可信变更链/来源桥，或人员明确确认的旧新行映射可以沿用该payment；位置不变、内容相似/完全相同都只作候选，不单独证明交易相同。

水单重排、approved/approvedAt变化、日期/金额/图片修正时，先判定“既有付款的新版本、既有付款新增证据、还是新增真实付款”，再处理相应版本和财务影响；不能因为来源哈希改变就新增付款。无法判定的55条无UID及后续同类记录冻结在stage，保留既有账面控制数，不推入新增收款。若旧源缺持久UID/变更日志，最终切换须冻结后逐项确认差异清单并固化逻辑ID，不能声称仅靠两次同批dry-run解决跨快照防重。

跨快照验收必须包含：旧两张图换序；仅审核字段变化；金额/日期修正；新增第三笔；另有一笔字段完全相同的合法新交易；删除后重新上传。每个观察行均可定位，但付款数和已收只随经确认的真实交易/调整变化。

建立每账控制：原`received`、可证明水单已收、台账已收、新系统已收及差额。若原已收无法由现存水单完整解释，保存受控`legacy_opening_balance`历史余额层，来源明确标“历史已收，证据待补”；它不是新付款、核销或银行交易，不伪造日期/入账或把余额归零。若原水单合计大于原received，也保留冲突待核，不擅自选一个。历史余额层与已证明付款层不能重复计入；每账给出勾稽公式和映射。

### 4.3 缺引用、删除和未知日期

12张缺客户、42张缺出运引用账单进入异常清单，保留金额、旧引用、显示名及现有付款。目标外键可暂为空并带`unresolved_source_ref`和待核状态；不制造占位客户/假柜。不影响历史余额查询和总账控制，新分配/需要该引用的操作须先确认关系。

回收站/墓碑优先于旧副本，不能借“补缺”复活测试账和已删客户。旧已审核无approvedAt时，审核状态保留、时间未知，今日核销不按付款日猜。旧布尔通知只代表历史标记；记录时间/操作者未知，不给它写导入当天来冒充刚通知。原本空号码、空仓、空汇率不补假值；公开查货号码不全就要求内部补录，不绕过验证。

### 4.4 两项目可能记录同一真实款项

110的已确认ledger先迁为银行核验与归档事实，不能无条件再加进MCSTAR已收总额。建立跨来源待关联列表：只有相同可信银行交易ID、明确已有来源桥或人工核实才可把110证据附到既有MCSTAR付款；姓名/日期/金额相同只提名候选。未确认前，110已核验但未绑定的款项显示为“未分配银行证据”，不新建已核销付款。

若找到已存在的MCSTAR付款，只补银行证据/claim和来源映射，不再生成一笔现金或第二份账单分配，不把补证当天计作新增核销。若原款仅存在于历史余额层，人工确认后将等额历史层重分类为可追溯付款/分配，保持该账已收与欠款总额不变，保存前后勾稽和原时间未知状态。若金额/币种/净贷记冲突，不自动重分类或修改旧款，列明差额待核。

只有明确证明是未入旧账的新款，才按新付款流程核销；无法说明“补旧证据还是新增收款”时不执行财务分配。该规则同时用于首次回填和后续110新消息补到旧水单的场景。

110原ledger/claim的有效占用随来源一起保留；未分配到MCSTAR时为verified_unallocated，已付款为posted，有争议为disputed，这三类均阻止再次领用银行款。不能在迁移重识别、队列恢复或correct/defer/retract时自动释放。证据失效与财务冲正按[集成方案](../integration/110集成方案.md)分别处理，冲正须显式财务动作及同事务勾稽。

## 5. 附件、历史和配置

1. 对`originalFile`、水单file、货堆/放货照片、MBL S/O和110原图/银行文件/模板/归档建立附件manifest。每项记录来源JSON指针或数据库行、文件类型、字节长度、SHA256、目标私有路径和业务关联。
2. base64先校验data URI、解码和实际文件类型，流式写临时文件，哈希通过后原子就位，再提交引用。空串、截断、不可读文件生成缺件/损坏问题，不写“已恢复”。
3. 同字节可共用一个物理对象，但每个来源/业务关联单独保存。37个file字段要逐一核实；23条没有file保留证据缺失，不合成图片。
4. 路径只接受来源manifest中的受控根目录，拒绝越界/任意网络URL抓取。旧地址若只是不可用链接，登记待找原件，不以一个可打开但错误文件替代。
5. 银行/媒体/会话/秘密分别分级；恢复备份全域覆盖但权限不同。原快照可能含历史凭据，作为访问受限的原证据保存，不复制成公开脱敏数据包；新业务备份不启用旧会话。
6. 通知/仓库/银行/价目配置保留来源和版本；未明确时效的旧全局汇率不代替每笔汇率；未核对模板/联系人不自动发布到首页。禁止顺便运行旧`mcstar_publish.py`等缺依赖部署脚本。

## 6. 工具契约与实际操作顺序

以下为**后续待实现的迁移工具契约**，不是当前已可运行的命令。每步有输入、输出、门槛及无副作用模式；本次只提供文档生成/校验工具。

| 顺序/操作 | 输入 | 输出及成功门槛 |
| --- | --- | --- |
| 1 `inventory` | 明确来源路径、数据集命名空间、生产/QA标签、读权限 | 全表/键/目录计数、版本、哈希、大小、未知字段与缺件清单。只能读。 |
| 2 `snapshot` | MCSTAR写入冻结/原子快照方法，110数据库与附件根 | 一致性快照manifest、采集/外发游标与时间窗口；可回读、非零文件、来源签认。 |
| 3 `stage` | 固定manifest及解析器版本 | 隔离staging、来源行映射、附件哈希及所有错误；不写正式表，不调用模型/WAHA。 |
| 4 `reconcile` | staging、角色/币种/时区/关系规则 | 每账金额、数量、库存来源、付款桥接、孤立/墓碑/缺件报告；所有阻断问题有处置。 |
| 5 `plan` | 已核对staging和目标空库/当前目标版本 | 可审阅create/update/void差异、目标ID、哈希及回退点；不修改业务。 |
| 6 `apply --dry-run` | 固定plan、空隔离目标、附件临时区 | 完整事务演练、相同批次二次运行0新增、附件/权限/余额回读。不会对外发送。 |
| 7 `apply` | 与review一致的plan哈希和受控目标 | 分实体批次提交、导入日志、幂等source_map；任一批次失败可断点重跑，不越过前置错误。 |
| 8 `verify` | 来源manifest、目标和附件 | 全域控制报告、逐账金额及历史状态对账、异常列表、无双占用/无复活记录，真实查询与原件回读。 |
| 9 `cutover` | 最终冻结快照、增量差异、交接代际 | 单写者切换，采集/外发仍保持已授权开关，不激活历史消息；旧系统只读。 |
| 10 `restore / rollback-plan` | 切换点、全量备份、WAL/增量、新事件清单 | 明确可恢复版本与新事件对账；空环境实际恢复验证后才能称成功。 |

### 一致性快照的取得

MCSTAR不能在进程正在覆盖JSON时随手读取半文件：先通过其受控导出或短暂停写取得原子副本，记录版本与哈希，确认业务数据/附件引用在同一切点。若历史服务没有一致性导出能力，需明确维护窗口短暂停写，不能假设copy天然一致。

110使用SQLite backup API或等价受控一致性备份，包含仍在WAL的已提交数据；不能只复制活动`intake.sqlite3`而漏掉WAL。附件以数据库快照可达引用生成manifest，复制后逐个校验；快照后新增文件属于下一增量。会话资产/秘密另受控交接，不能把运行中的同一会话克隆进测试机。

### 目标写入顺序和事务

先迁来源/附件manifest、身份/单位/仓库/配置，再迁收据来源、出运/明细及其版本，接着账单、证据/银行、历史付款桥接/分配/余额层，最后迁节点、通知、单证、历史审计与暂停队列。每批先检查依赖映射；未知外键保持明确待核，不凭空创建父实体。

单据/付款聚合内事务原子，跨文件对象先准备后提交引用；数据库失败时临时对象保留待清理清单，未经检查不自动递归删除。每次apply同时写迁移run与source_map。再次运行同一manifest+规则版只返回已有目标；规则变更需新plan与差异，不用新的run ID绕过幂等。

## 7. 对账与签收标准

| 检查层次 | 必须对照的内容 | 允许的差异 |
| --- | --- | --- |
| 来源覆盖 | 每个键/表/字段/文件均有目标或明确历史/排除理由 | 旧令牌不激活、QA不进live等预先列明的排除；未知不算已覆盖。 |
| 原始计数 | 28主单、964原行、619账、60水单、73台账等与新批次最新数逐项核对 | 正规化后表行数可不同，但来源行到目标的映射必须完整，不能只比新表总数。 |
| 财务 | 每账应收/应付、原币、NGN、已收/付、折扣、未结，按客户/出运/币种/状态汇总 | 来源本身冲突保留原数+待核层；禁止未解释的分位差额或重算覆盖。 |
| 付款桥接 | 每条来源水单/ledger归属、同笔多表现、两笔合法同额、55无UID | 不确定关系待核；不能为凑总数合并或新增现金。 |
| 银行 | 原行与可信交易、当前claim、撤回/复核、live/sample | 同源重传可复用物理文件和规范交易，原始行/来源不丢。 |
| 库存 | 原生入库、改包/作废、各批出入库、剩余 | 缺原生台账只显示来源缺口，不能由出运历史倒推当前库存为已证实。 |
| 状态 | 审核、通知/装柜标记、控货/信用、实际提货、主分节点覆盖 | 未知时间/人保持未知；导入时间单独存，不补成业务时间。 |
| 删除/历史 | 墓碑、回收站、旧副本与历史版本 | 删除体可归档，不回active，不重新发通知。 |
| 附件 | 每引用的存在性、类型、字节哈希及受权取回 | 确认的缺件清单仍显示未完成，不能当成功复制。 |
| 隔离与权限 | live/sample、客户范围、仓库范围、秘密/令牌、公开入口 | 不允许财务/客户信息越界；旧会话未激活。 |

回填结果至少生成四类报告：来源覆盖表、金额/状态勾稽表、异常及人工处置表、附件哈希/缺件表。公开摘要只含脱敏统计；实际金额/号码/图片在受控报告中。新生产快照每次都重新生成，而不是复用本文旧计数签收。

## 8. 切换与回退

1. 先在隔离环境完成全功能与两次幂等回填、恢复演练；新系统不开采集/外发、不改变旧生产。必须补齐正式来源，对不能开放的缺模块明确标示，不以样本库替代。
2. 切换窗口冻结旧系统写账、上传、出入库与复核，记录最后业务版本、消息/队列游标、已发送和不确定状态。冻结采集如造成漏消息窗口，记录起止和可核实补采范围；没有证据不能称零丢失。
3. 取最终一致性快照，生成相对试迁差异，重点复核无ID票件重排、付款状态、银行占用、删除及新附件。增量不明的聚合停在待核，不强行用行号接续。
4. 最终导入、对账通过后切新内部入口及Webhook唯一消费路由。使用代际标记/租约锁控制只有一个有效业务写者与一个有效发送者。旧系统只读，禁止其旧页面继续缓存后回写。
5. 保持原暂停/只读状态；如之后明确启用采集或发送，只处理经确认起点后的授权范围，不因部署自动开关。外发`sent`和`uncertain`历史均不可自动重试。
6. **新系统尚无业务新写入：** 可切回旧只读切点对应的完整备份及附件，并明确维护期间未处理动作。**已经有新付款/出库/审核：** 先停新写与外发，导出新事件/附件/银行占用，核对后向旧系统兼容回放或修复新系统；不能直接拿旧快照覆盖新库。
7. 银行转账、已发消息、实物提货是外部事实，数据库回退不能撤销这些事实。回退必须保留其回执/现场依据，避免再次核销、重复发送或重复出库。
8. 回退/恢复演练报告记录输入版本、哈希、恢复后来源映射、金额与附件核对及未完成项；业务负责人核对真实结果后，才能写“迁移完成”。
