# 规模验证与实际优化

所有负载在自有合成schema执行，没有生产客户/模型/采集/发送。25k和125k两种规模，各10个独立授权会话、每组6轮×8操作=480个请求，包含50行列表/搜索、票件复核与幂等重放、银行50候选匹配/复核/重放。p95按nearest-rank计算；后期组在全部10账号登录后才放行业务负载，warmup为0。冷登录/首个查询波峰单列，未降低Argon2强度。

具体优化不是新的财务算法：

1. `packing/service.py`和`packing/allocation.py`批量取得页面票件的组件、到货、报价、附件和实际提货投影。50行重复查库从451个SELECT降至有界批量查询，权限与单票投影一致性由测试验证。页面响应仍随50行明细数量增长。
2. `bank/service.py`批量原始行/文件/占用查询，50个合法同额候选完整保留；去掉逐候选N+1查询，不能通过少查候选来提高速度。
3. `g11000600002`按created_at/id以及warehouse/created_at/id增加分页排序索引。相同实测SQL计划94.846ms降至0.276ms。数据库索引查找约O(logN+页大小)，模糊包含搜索仍可能扫描授权候选，不宣称所有查询常数时间。
4. `migration/bundle_stream.py`及`backup.py`对兼容format1逐行编码/解析、增量SHA256、每1000行插入和回读，保留REPEATABLE READ、checkpoint、逐表hash、附件、权限及空库栅栏。`operations.fact_snapshot`使用分批数据库游标，仍保留O(N)事实元数据。

SHA256按字节增量计算，但JSON framing并非另一个恒定成本解析器：它在块未包含完整单行对象时用标准库重试解析。若单行极大，重试会重复扫描前缀，最坏时间可随该行大小呈二次增长；单行本身及1000行插入批次也必须驻留内存。此次测试的行分布和结果不能外推为任意巨型单行的线性时间保证。

125001行库存导出通过真实HTTP排队、local worker、下载XLSX和行数回读。最终进程树测量：排队4.440s、worker50.405s、整体74.626s、文件3,639,931B、worker峰值1,010,774,016B。前一轮排队0.137s/整体69.986s的记录保留，但其3.5MB内存只测到venv启动器，明确无效；修正后的采样包含真正Python子进程。

API组峰值520,704,000B；自有PG进程树Working Set加和1,378,504,704B。API不包含数据库/worker；PG共享页可能被各进程重复计数，也包含该自有cluster其他空闲应用连接。worker每100ms、HTTP组每50ms采样会遗漏更短峰值，均不是整机或唯一物理RSS。不能据这些数值承诺旧8GB机器一定够用。

详细p50/p95/max、各请求结果、人口与源文件hash、源码清单和采样PID保存在受控benchmark收据；公开版本只含合成统计。最终全应用回归和包复建另记，不能把性能组旧hash冒充最终完整应用freeze。
