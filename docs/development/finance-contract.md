# Finance, bank, evidence and channels contract

Task 2 backend contract, 2026-11-04. Public production collection, paid recognition, real WhatsApp delivery and complete logistics release integration are **not accepted by these local tests**. No external account was started. All money is serialized as decimal strings; timestamps are UTC ISO strings, calendar dates are ISO dates.

## Transactions and downstream integration

Every command has signature `(db: Session, actor: Actor, payload: dict) -> dict`. Payload includes a nonempty `idempotency_key`; services own neither commit nor a nested transaction. HTTP supplies `Idempotency-Key` and uses the foundation's function-scoped `Database` plus `mutate`. Non-HTTP callers own `with db.begin()` and set `db.info['settings']` for files, totals and worker queues. Unknown command fields fail. Every command uses `run_command`, audit and scoped permissions, including full current action/read/related-resource permissions before returning an idempotent replay. Cached snapshots also retain authorization to their original source/account relationships. Authorized recovery does not recheck obsolete expected versions or used-action expiry; changed payloads still conflict. Changed commands require `expected_version`; target row locks refresh the identity map after waiting.

Task 2 currently uses one PostgreSQL transaction advisory guard (`110002`) to order short finance/evidence/bank command mutations consistently, with row locks and active-claim unique indexes as database enforcement. This intentionally prioritizes correctness; cross-party throughput has **not** been benchmarked. No model or WAHA call occurs in this guard. Workbook preview/archive/export currently perform bounded local work within their command transaction; asynchronous bulk scheduling belongs to Task 5 and representative workload assessment to Task 6. Do not promise p95 throughput from these tests.

Task 3 must call `create_invoice` only after its owning arrival/manual creation checks and retain initial `uploaded_on` on replacement. Task 2 has no cargo tables or arrival inference. `source_key` must be a stable, namespaced original identity, never receipt number/name/date/amount. It is optional and globally unique when supplied. Future cargo-to-invoice joins must use real entity IDs, preserving all repeated source lines.

Task 3 repricing flow:

1. Load original invoice and display `adjustment_preview(db, actor, invoice_id, amount_ngn, discount_total_ngn=None)`.
2. Submit `adjust_invoice` with the complete returned `preview`, expected invoice version, new amount, reason and any explicitly confirmed discount total/new charge components. Preview includes version, old/new amount, original payment cash, historical credit, current allocation, old/new discount, credit returned, outstanding and `invalidate_unexecuted_instructions`.
3. The service records `InvoiceAdjustment`, signed reverse `Allocation` entries and any explicit signed `Discount` adjustment. Original payment cash/approval/claim remains. A fully allocated 100000 repriced to 80000 leaves 80000 allocated and 20000 available; repriced to 120000 leaves 20000 debt. `due_on` is unchanged. If components are not supplied, changed totals are explicitly manual totals; original components remain in the audit snapshot, not as stale current components.
4. Consume `FinanceEvent` in the same business transaction where applicable, and enforce pending invalidations before executing a release. Events have nullable `invoice_id`, nullable `payment_id`, `kind` (`invoice_changed`, `payment_reversed`, `evidence_disputed`) and nullable `processed_at`. Task 4 owns superseding unexecuted release instructions and pausing pending deliveries; it must preserve actual pickup/previous delivery facts. **This event alone does not mean release records already changed.** Events naming a payment affect every invoice with its allocation history.

Financial state does not encode UI yellow/red, manufacturer hold, freight credit release or physical pickup. Task 4 owns those independent facts; AR-03 yellow requires a release instruction for partial payments, or a separate credit release.

An allocation is `{invoice_id, expected_version, amount_ngn}`. Duplicate invoice IDs, cross-scope/direction allocations, over-allocation or disputed payments fail atomically. One real customer and bank account retain one identity across explicitly authorized warehouse memberships. A payment may allocate same-party invoices across those warehouses, with permissions checked on every affected invoice, payment origin, allocation-history warehouse and linked evidence warehouse. Cross-party allocation is rejected unless the separate controlled path below is supplied. Many payments may settle one invoice; one payment may settle many invoices. Existing posted payments can allocate remaining credit without changing original approved_at. `pay_payable` creates an outgoing approved payment by party+period with no shipment requirement. Optional invoice allocation is not required to pay the period. Period balance is billed total minus discounts and unique posted outgoing payments across the entire same-party/period/live-sample scope, including authorized multiple warehouses. The request warehouse is an access context, not a partition that duplicates the one cash record. The response adds discount_ngn and warehouse_ids; missing access to any involved warehouse denies the complete period view.

FX payload shapes are exact: NGN uses no fx or `{direction:'NATIVE'}`; USD uses `{direction:'NGN_PER_USD',rate:'1500'}`; CNY uses `{direction:'NGN_PER_CNY',rate:'...'}` or `{direction:'USD_CNY_CROSS',ngn_per_usd:'1500',cny_per_usd:'7'}`. Cross CNY settlement = CNY ÷ CNY/USD × NGN/USD. NGN never uses an FX multiplier. `charge_amount(unit_price,currency,unit,quantity,fx)` supports USD/NGN and KG/CBM/PCS, whole integer PCS. NGN2000×3PCS=6000. Amounts have two places, rates/quantity six, computed line amounts use HALF_UP. An invoice with charge components must equal `charge_usd × ngn_per_usd + charge_ngn`; rate is required only for nonzero USD.

Invoices return `allocated_ngn`, `discount_ngn`, `outstanding_ngn`; payments return `allocated_ngn`, `available_ngn`. Pending/reversed payments have zero usable balance. Tail `waiver=true` requires the exact positive remaining balance and at most NGN5000, exclusively a ledger discount; it is never bank tolerance. Discount greater than new price requires an explicit legal new discount total in the same confirmed price command.

Approved export rejects incomplete access instead of emitting a partial full-day archive. Export responses and their immutable audit provenance retain source_payment_ids/source_claim_ids; cached responses and later file reads recheck every related current warehouse/account right. Legacy export artifacts lacking this provenance are restricted to administrator review. Historical files remain evidence after a later dispute; new archive generation still requires a current verified bank basis. ### Same-image source assessment (Tasks 6/7)

Equal SHA is only an image-bytes fact. For an existing image SHA, attaching another accepted source compares original caption/related-message text after whitespace normalization; IDs, sending timestamps and repeated identical text are not transaction changes. No new substantive text preserves the existing verification automatically. New substantive wording without an authorized assessment is recorded as **unknown / pending review**, not asserted to be a semantic contradiction; the current occupied claim/payment verification is disputed, preserving cash, allocations, occupancy and historical archive bytes. There is no keyword classifier or semantic model call.

An authorized reviewer can confirm equivalent wording or another explicit observation of the same payment without cancelling a valid verification:

1. GET `/api/evidence/{id}/source-assessment-preview?attachment_id=...&message_id=...` (message_id optional for a manual original). Returns case_id, case_version, attachment_id/image_sha256, message_id, all eight current `fields` including explicit nulls, original `context`, normalized `source_texts` and `source_fingerprint`. Requires evidence.read/review, original attachment access and all source/context read rights. With an active bank claim it additionally requires bank.review on the occupied original account, current selected account and every affected payment warehouse.
2. Submit `/api/evidence/{id}/images` with the returned case_version as expected_version. On the exact image row include `source_assessment:{verdict:'corroborates'|'contradicts'|'unknown',reason,fields,source_fingerprint}`. `fields` must exactly include **all** current transaction fields, including unknown/null; empty/partial/chosen-only fields, changed fields, a blank reason or a stale/other source fingerprint fail. The fingerprint binds this case/version, attachment/SHA, message ID, substantive text and full reviewed fields. It is an evidence snapshot token, not an authorization substitute. Preview and mutation enforce the same assessment rights; replay rechecks current rights, including the original reviewed claim relationship.
3. `corroborates` is an explicit human assertion that all reviewed transaction facts still describe the same genuine payment; it allows already-known image bytes and equivalent/new confirming wording to preserve the current verification. `contradicts` and `unknown` require current review and freeze the current verification. The service does not silently apply a corrected amount/date/transaction identity from prose. Use the existing versioned field correction and explicit bank revalidation paths. A corroboration never automatically restores an already disputed claim, and never bypasses review of genuinely new image bytes.

Each assessed or unassessed new-text observation writes EvidenceReview(action=source_assessment) with image/message binding, raw source context, reviewed field snapshot, case version, fingerprint, assessment kind/verdict, actor and reason. It does not delete/rewrite historical archives or reverse/release cash. New text arriving after preview changes the bound snapshot and requires reload. HTTP serialization preserves explicit unknown fields. A web form or Task 7 tool must show the source and complete fields to the reviewer; it must not silently manufacture a corroborates verdict.

Bank match idempotent replay authorizes **every original selected/candidate BankEntry account** represented in the saved result, even after the case is rebound or its account cleared. Revoking the original account membership blocks cached candidate disclosure; retaining all required rights permits recovery with the original expected_version.

GET `/evidence/{id}`, `/evidence-jobs/{id}`, `/bank/imports/{id}` require scoped read capabilities. GET `/finance/files/{attachment_id}` verifies domain relationships and scoped evidence.read/bank.read/bank.export/finance.export, checks original SHA and forces private no-store download. Generic upload remains the foundation self-owned `/attachments`; original image/file bytes remain immutable. No public bank routes exist.

`python -m app.domain_worker recognition` runs one leased job; `delivery` runs one gated delivery; `media --operator-id UUID` runs one accepted-message download under fresh grants. No startup hook launches workers. Recognition client is the ported whole-image VisionClient with supported-field parsing; unmatched whole-image extraction schedules the ported located-field/fixed-band zoom stage. It persists per-image original candidates/evidence/normalizations/result, tracks leases/retries and rejects stale case versions/profile changes. The worker uses no transaction during network calls. Only an explicit human case review writes normalized fields. Disabled/unconfigured recognition returns provider_unavailable without a call. Model environment follows the adapted `MULTIMODAL_ENABLED/BASE_URL/API_KEY/MODEL` and global Settings.model_calls_enabled. Secrets stay in deployment environment; never include them in payloads or docs.

## Signed dual-entry channel boundary

**Implemented boundary:** this task supplies the structured prepare_action/nonce/execute APIs and shared financial/evidence actions described below. It does **not** yet implement a natural-language webpage/assistant turn → model tool loop, a complete query/archive intent dispatcher, or end-to-end assistant response orchestration. The standalone archive service and HTTP route are functional, but chat cannot be advertised as having a complete archive/query dispatcher. **Connection-management gap:** no WAHA session-status, QR/pairing, bounded recovery or connection-alert management adapter is implemented by Task 2. The current adapter covers signed intake, exact accepted-message media retrieval and gated delivery only. Existing read-only source connection logic was inspected as context; source inspection and default shutdown do not constitute a migrated connection manager. These capabilities remain in the full design for a separately verified integration task, with account startup/login still requiring the applicable explicit authorization.

`POST /api/webhooks/waha` is the sole non-session mutation here. It requires body HMAC-SHA512 in `X-Webhook-Hmac`, algorithm `sha512`, max 1MiB, allowed session/chat and generation, explicit capture start, stable message identity, non-self/bot message and valid source time. It rejects historical/future messages, preserves duplicate source identity, and refuses conflicting source contents. Collection defaults paused. Ingress records source and queues exact accepted-message media download only; it never requests chat history, marks read, starts or pairs an account.

Configuration is environment-only `MCSTAR_WAHA_` followed by WEBHOOK_KEY, API_KEY, BASE_URL, INSTANCE, GENERATION, CAPTURE_SESSION, ASSISTANT_SESSION, MAIN_SESSION, SINCE, SCOPE, GROUPS (chat→warehouse JSON), OPERATORS (sender→user ID JSON), RECIPIENTS (JSON allowlist). No new-message collection is authorized by merely configuring an adapter. Deferred media and recognition recheck current source ownership before provider I/O, including instance, generation, group-to-warehouse mapping, scope and capture start; context sources have the same ownership and individually authorized read access. A changed configuration never silently rebinds old provenance. Stored historical evidence remains readable with its original ownership grants, while stale context cannot be sent to a provider under a newer capture boundary.

POST `/channels/actions`: `{message_id,action,payload,text?}`; capabilities channels.act plus target action capability. `action` is payment.post/evidence.review/bank.review. Signed source text containing a question/condition is never executed. The sender must map to the current actor; target and message warehouse/scope must agree. Multi-invoice or incomplete chat distributions return `web_confirmation_required` with an authenticated webpage path. Otherwise response contains stored action id, preview, expires_at and an explicit `/confirm <id> <nonce>` command. Both originating and confirmation sources are revalidated against current configuration. It rechecks current actor capabilities, scope and all business versions, calls the same finance/evidence/bank method as the webpage, and returns `executed:true` only after that transaction succeeds. Model text alone cannot assert completion.

Main session always fails. Delivery worker refreshes the actor, originating warehouse grant, current sender/operator mapping and complete source boundary immediately before I/O, blocking stale work, and writes sending before I/O; confirmed provider receipt becomes delivered. Timeout, nonconfirmed response or expired sending lease becomes uncertain and is never automatically replayed. No test sent a real message.

## Task 3 source-validated allocation integration

The logistics contract now owns the detailed typed `CargoChargeComponent` and actual-arrival allocation rules (`logistics-contract.md`). `Invoice.rounding_adjustment_ngn` is signed NUMERIC, default zero for old invoices. Amount = shared HALF_UP USD settlement + native NGN + this explicit difference. It is never a synthetic clearing/freight fee. Public invoice HTTP input does not expose arbitrary rounding or a caller-invented `rounding_basis`.

Internal cargo create/adjust/preview validates the entire basis against current typed tickets, actual arrivals, immutable component revision IDs/versions/units/source amounts, physical quantity controls, explicit FX and original invoice relationship. Components and NGN settlement both obey their cumulative actually-arrived quotas; the final batch takes the nonnegative exact remainder. `ArrivalSettlement` plus invoice pricing/audit retain each applied proof. Downstream documents/UI must show a nonzero rounding difference explicitly.

An old related AR remains authoritative when component decomposition or allocation units are unknown, including older `arrival_allocation` snapshots predating typed components. New actual arrivals remain pending finance and never recalculate that old AR from the full source total. Resolving that state requires explicit reviewed `charge_components`, current ticket version, and full financial preview. Even when the resulting amount happens to equal the old AR, replacing its source proof requires a finance adjustment/version/audit; payment cash and historical allocations remain intact. Future actual batches then use the reviewed component units against the same invoice ID.

Protected logistics replacement-history cash snapshots are stored with original invoice/payment IDs and original warehouse scope provenance. Ordinary logistics revision projections omit them; the dedicated history endpoint requires current finance.read on those original sources and current payment scopes independently of current document membership. Split/move or revoked read access does not authorize old cash snapshots.
