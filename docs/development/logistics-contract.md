# Logistics, warehouse, pricing and party contract

Task 3 implementation, 2026-11-04. These are local backend interfaces and evidence boundaries, not production migration, browser/template acceptance, live account pairing, paid model execution, or physical-release acceptance. No external account, model, collection or sending service was enabled.

## Transaction and permission rules

All commands use `(db, actor, payload) -> dict`, own no commit, and take `idempotency_key`. HTTP supplies `Idempotency-Key`, authenticated session and CSRF through the existing function-scoped `Database`/`mutate` dependencies. Dirty fields only; unknown command fields fail. Typed HTTP models are in `app.api.logistics_inputs`, with additional independent domain validation. Every changed target requires `expected_version`; batch entries carry their own receipt versions. Same-key/same-body recovers the original result; a different body conflicts. Every command audits in the same transaction.

All logistics mutations take financial advisory guard **110002 before command-key locks and domain row locks**. This deliberately serializes short mutations across finance and logistics, rather than claiming benchmarked throughput. Original workbook parsing, model I/O, and Excel rendering run outside these mutation locks. Both the action capability and its domain's `.read` capability are required. Both scopes are checked before work and against the original returned warehouse/source graph on replay. Financial orchestration revalidates invoice read/create/adjust and related payment scopes on replay, including discount permission for explicit or nested replacement discount resolution. Warehouse IDs are immutable on receipts, tickets, shipments and documents. Party identity edits require all active memberships; membership commands remain the shared finance service.

Capabilities: `cargo.read/manage/dispatch/review/export`, `packing.read/manage/import/arrive/review`, `shipments.read/manage`, `pricing.read/manage`, `parties.read/manage`, `warehouses.read/manage`, and the shared financial capabilities for related changes. Ordinary entry permission does not confer supervisor review. Internal reads never authorize anonymous/customer access; Task 4 must implement its own minimum projections.

## Original file preview, commit and replacement

`app.packing.imports.preview_import`: `{warehouse_id,attachment_id,kind:'packing'|'f6',mapping?}`. Attachment must belong to the actor or be explicitly administratively authorized; original bytes stay private/checksummed. It reads XLS/XLSX, every worksheet in order, explicit merged ranges, segmented warehouse-address context, English/draft/F6 aliases, gross KG excluding NET, CONTACT NUMBER, and separate USD/NGN columns. `P.H`/`PH` normalize to PORT HARCOURT. Unknown destination remains NULL; ONNE never picks a customer's destination warehouse.

Supplied files format empty cells through XFD. The parser bounds **actual nonempty data** instead of treating formatting-only XFD as 16,384 business columns. Caps: 25 MB compressed, 100 MB expanded, 200 sheets, 30,000 actual rows/100 actual columns per sheet, 200,000 populated cells per sheet. Data beyond these bounds fails explicitly. Raw source remains in the original attachment. A footer/notes row is retained as source evidence but not cargo. Exact TOTAL/GRAND TOTAL/合计/小计 terminators can be in any column. Missing identity and malformed quantities remain reviewable issues, never invented ROW numbers or silently deduplicated receipts.

Mapping format is `{sheet_name:{fields:{field:{column:zero_based_index,basis?:'total'|'CBM'|'KG'|'PCS'}}}}`. Only supported source fields are accepted. Rate multiplication follows explicit source semantics. A label such as `CLEARING CHARGE PER CBM TOTAL` is **ambiguous**: raw amount retained, normalized charge NULL with `clearing_ngn_basis_unconfirmed`; the reviewer must choose its basis. Magnitude-based rate guessing is not used. Fee issue counts do not imply confirmed charges.

`commit_import`: `{id,expected_version,selection:[{row_id,values?,native_receipt_id?}],excluded_rows?:[{row_id,reason}],shipment_id?,reference?,uploaded_on?}`. Every candidate cargo row must be selected or explicitly excluded with a reason. Values are explicit reviewed corrections; missing quantities can remain NULL on imported tickets. F6 commits retain source rows and optional native links, **without adding StockEvent**. Every eligible row persists `disposition=selected|excluded`, `exclusion_reason`, `reviewed_by` and version. `/f6` includes only selected committed rows; excluded raw observations remain accessible in their authorized import preview. Legacy committed rows with no retrievable selection evidence stay pending rather than being silently selected. Packing commits add independent document/ticket identities, original row order and revision. Full-document multiple sheets are not deduplicated by receipt/name/value: select/exclude reviewed duplicate observations explicitly.

`replacement_preview(db,actor,document_id,batch_id,mapping,excluded_rows=None)` takes explicit `[{row_id,ticket_id|null,values?,discount_total_ngn?}]`. Every new candidate row must map once or be explicitly excluded once with `{row_id,reason}`; every current active ticket must still map once. Unknown rows stay unresolved until selected/corrected. Row index is not inferred identity. Replacement POST includes the exact returned preview, target document version, mapping, exclusions and reason. Exclusion reasons are bound into the exact preview/revision and stored on retained source observations; changing a reason requires a new preview. Financial source proofs are revalidated in the transaction. Existing ticket IDs, invoices/due dates/payments/discounts, arrivals and attachment relationships survive reordering. All original batch attachments/revisions remain. Removing a previously billed ticket requires the explicit reviewed business-void path rather than an omission from the new file.

All preview families require current domain read plus action permission, including both original document and new import source. A billed preview also requires current finance read and adjustment authority across invoice and every original related payment warehouse.

Native receipt links are explicit references, never inferred by matching. Create/edit/import/replacement validate `cargo.read`, warehouse equality, active state, and known receipt text, Party and transport compatibility before assigning a new non-NULL link or changing its identity fields. The old source independently requires current `cargo.read` and its warehouse scope, but its old lifecycle/relationship need not qualify as a new assignment: authorized operators can unlink a void receipt or repair a historical wrong-warehouse link. Ticket/document expected versions and retained old/new source IDs still apply. Command replay checks current authorization of stored original and current references even after unlinking; a later receipt void does not invalidate a previously successful command result or execute it again. Revoked original-source access still denies replay.

Ordinary document/group/command projections omit `finance_preview` and `financial_sources` from revision differences. The immutable DB revisions remain complete. `GET /packing/documents/{id}/history` returns protected history only after current packing read plus finance read for each original invoice, original payment IDs and captured source warehouse set. Current payment scopes are checked too. Replace then split does not discard or weaken that source authorization. Pre-fix revisions resolve retained stable ticket IDs and historical allocation links; unresolved protected sources are denied.

## Arrivals, split, void/recover and financial settlement

`create_ticket` never creates AR. `arrive`: `{id,expected_version,pieces,kg,cbm,occurred_on,source,mode:'air'|'sea'}`. AIR/EXPRESS use air mode; SEA rejects the air-only action. Actual arrival quantity cannot exceed ticket totals; final pieces consume the exact remaining weight/volume. Missing price/FX is pending finance, not invented zero. Newly eligible arrivals create one stable `source_key='ticket:'+ticket.id` AR; later batches adjust the **same** invoice to the arrived share. Unarrived portions are not billed by this automatic path.

Both currency totals and their nonzero components' reviewed quantity bases must be explicit before new automatic AR: a source NULL clearing/freight component is unknown, not zero. An explicit zero or a confirmed all-in/single-currency quote snapshot may legitimately provide the zero non-applicable component. The known AIR/EXPRESS all-in and NGN/PCS quote paths retain this behavior. Actual arrivals can be recorded with unresolved new charges and later priced through the ticket command. A historical related AR with unknown component decomposition is preserved when recording an additional actual arrival.

Historical/manual related AR without reliable reviewed component units is retained unchanged by new arrival eligibility, including pre-component `arrival_allocation` proofs. The state is pending component review, not a missing invoice. Resolution requires explicit `charge_components`, current ticket version, and the complete current `finance_preview`; a source-proof revision is financially previewed/versioned/audited even when the amount is unchanged. Existing invoice ID, original cash, allocation history and due date survive. Later arrivals resume incremental billing only from that explicitly reviewed basis. It is not shrunk/deleted/recreated merely because the current automatic rule differs. Independent finance edits invalidate automatic allocation assumptions and require review. Explicit ticket edit/replacement can still update existing AR through shared `adjustment_preview`/`adjust_invoice` with current full impact, original cash and due date preserved.

`ticket_change_preview(db,actor,id,changes)` computes prospective quote/components and financial preview without persisting a quote. POST ticket edit includes the matching `finance_preview` when related amounts change. Manual unit prices remain authoritative across destination repricing; direct reviewed totals supersede prior unit-rate snapshots. A missing new rate leaves unbilled cargo pending; an already-billed ticket must provide an explicit reviewed replacement price instead of silently losing its financial basis.

`Ticket.pricing_authority` is a server-controlled enum exposed on detail/list and change preview:

| State | Current authority and permitted transition |
| --- | --- |
| `quote` | `quote_id`/`quote` is the effective immutable unit-rate snapshot. Confirmed manual unit rates multiply the actual PCS/KG/CBM quantity on later edits. An explicit `manual` decision replaces that unit rate. |
| `totals` | Explicit currency totals or reviewed `charge_components` control the original bill. Current `quote_id`/`quote` is NULL; obsolete snapshots and revision/audit history remain stored. Metadata edits, including destination, preserve totals and never silently load the old quote or a default card. |
| `pending` | No confirmed applicable quote or explicit charge total. Unknown components remain NULL, and arrival does not invent an AR. |
| `review` | Migrated authority is unknown. API current `quote_id`/`quote` is NULL; `historical_quote_id` exposes the retained old reference only as history. Metadata corrections and actual arrivals are allowed while existing AR/cash/allocation facts remain unchanged; new automatic pricing/allocation awaits explicit review. |

For `totals`/`review`, changing PCS/KG/CBM without a new pricing decision returns 409 `pricing_decision_required`. Ticket PATCH/change-preview accepts `repricing:'retain_totals'` with a nonempty `reason`, retaining the explicit bill for the new quantities, or `repricing:'quote'` to deliberately select a current default card. Explicit `manual:{unit,currency,unit_price,source}` selects a confirmed new manual rate; no rate is inferred by dividing an old total. Explicit quote selection without an applicable card returns 409 `quote_unavailable` and preserves the old state. Mixed totals and quote decisions are rejected. Direct reviewed totals/components enter `totals`; missing legacy component units still require explicit component review before allocation. Existing billed repricing/source revisions use the complete financial preview/version/audit even at equal amounts. Contact/destination-only metadata edits do not require inventing a new financial source or overwrite a legacy AR.

Initial imports, replacement previews/commits and ordinary edits share these authority rules. Reviewed source totals/components supersede prior quotes during replacement; later metadata edits preserve that decision. Historical quote/component revisions are never overwritten. Task 4/5/6 must present current versus historical quotes distinctly, show `review` as unresolved authority, and supply an explicit quantity/repricing decision rather than copying a historical quote into a new request. Stable ticket/invoice identity and the independent source-version rules below remain unchanged.

`CargoChargeComponent` stores `quote_id` XOR `ticket_id`, `ticket_version`, `position`, `component:freight|clearing`, `currency:USD|NGN`, `unit:PCS|KG|CBM`, nullable original `amount`, and explicit `source`. Quote lines and ticket revision sets are append-only via the service. The effective set is the latest ticket revision at or before the current ticket version; previous sets are never overwritten. `TicketFields.charge_components` accepts the five reviewed component fields; any simultaneously supplied currency totals must equal their sums. Existing one-line currency totals can be revised while retaining the confirmed unit; changed multi-line totals require explicit component review. Quotes establish actual card/manual units; source parsing establishes units only from unambiguous unit headers. Legacy total-only prices do not gain an inferred transport-based unit. Actual arrivals can remain unpriced until review; existing historical AR remains unchanged.

SEA card NULL clearing propagates through the quote and ticket as unknown, including `QuoteSnapshot.charge_ngn` and total. Explicitly reviewed zero resolves it. AIR all-in and explicit single-currency/manual zero paths remain supported. A NGN2000/PCS line for 3PCS/30KG allocates NGN2000 to the first 1PCS/1KG. A separate NGN100/CBM clearing line adds only NGN50 for that batch's 0.5CBM.

**Rounding allocates original source charges.** A component with total `T`, original unit quantity `Q`, this batch quantity `q`, cumulative arrived quantity `C`, and previously allocated amount `U` receives `min(HALF_UP(T*q/Q), T-U, max(0, HALF_UP(T*C/Q)-U))`. All amounts are cents; the fully arrived batch receives `T-U`. Each component uses its own reviewed PCS/KG/CBM. NGN settlement is separately capped by both remaining original settlement control and the cumulative quota `sum(HALF_UP(component_total * FX_if_USD * component_arrived_quantity / original_component_quantity))`; the final actual batch receives the remaining control. Thus neither original-currency components nor NGN may prebill unarrived portions beyond the explicit cent rounding. The resulting cumulative difference from aggregate USD×FX+native NGN is stored in typed `Invoice.rounding_adjustment_ngn`; it is never presented as clearing or freight. Invoice amount = USD×FX + NGN + explicit validated rounding.

Example: original USD1, FX1.5, three equal batches → USD .33/.33/.34; settled NGN .50/.50/.50; cumulative AR .50/1.00/1.50; cumulative rounding .00/.01/.00. Native NGN1 → .33/.33/.34 and total1.00. Mixed USD1+NGN1 at FX1.5 → .83/.83/.84 and total2.50. A NGN1 payment after batch2 remains actual NGN1 after batch3; final due .50. USD .02 in four equal physical batches allocates .01/0/.01/0, never a negative remainder. USD .10 at FX1.5 in ten equal batches has cumulative NGN capped at HALF_UP(.15 * arrived_fraction); it cannot reach the full .15 at batch8.

The internal finance `rounding_basis` contains exact current ticket/version, arrival IDs/versions, immutable component IDs/versions/kind/unit/source/amount, original source quantities, FX, warehouse/party and control. `app.finance.rounding.validate_basis` recomputes this from real typed rows; any forged amount/basis or wrong invoice relationship is rejected. No public invoice HTTP input exposes arbitrary rounding or `rounding_basis`. Current finance previews/get/list/audit include old/new rounding; approved-payment Excel has a separate deduplicated **Invoice components** sheet exposing nonzero rounding without double-counting payment cash. `ArrivalSettlement` preserves each applied invoice-version allocation. Old invoices gain rounding zero without recalculating their values.

`split_document`: select explicit ticket IDs and child reference. It moves stable ticket membership, keeping invoice IDs, allocations, payment cash, source rows and ticket attachments. Parent and moved ticket versions change; child records parent and inherited original revisions. No invoice or cash is cloned.

`void_preview`/`void_document`: preview all related tickets/invoices and confirm document version/reason. Shared finance adjustment to zero and explicit discount resolution writes reverse allocation credits; invoices and tickets become void, original cash/evidence/arrivals remain. `recover_preview`/`recover_document` require a new complete financial restoration preview. Cargo/AR can be restored, but previously returned cash stays unallocated until a separate authorized allocation command. Actual pickup records, once Task 4 owns them, must never be deleted/reversed by these operations.

`ticket_void_preview`/`void_ticket` apply the same reviewed zero-charge/reverse-allocation policy to one explicitly selected ticket. Its sibling tickets and document remain active, permitting a subsequent replacement mapping to omit that already-void ticket without physical deletion. Target ticket and document versions change; the void ticket's original row, arrival, invoice and payment history remain available.

Clearing AP uses one `Shipment.clearing_invoice_id` and namespaced source key. Repeated identical saves do not duplicate AP; changed costs use shared reviewed financial adjustment. Creditor replacement on an existing payable requires explicit ownership resolution rather than silently transferring a paid debt. Initial upload/due date is preserved.

## Task 4 source-version boundary

The stable graph is `Receipt → StockEvent/DispatchBatch → Shipment → PackingDocument → Ticket → Arrival`, with optional `Ticket.native_receipt_id`, `Ticket.invoice_id`, ticket attachments and source rows. Splitting changes `Ticket.document_id` and increments ticket/parent versions. Replacing retains ticket IDs but increments affected tickets/document. Dirty edits, quotes, reviews and attachment changes increment their target versions; ticket edits/arrivals also increment their document; arrival updates shipment state/version. Warehouse/Party configuration has its own versions.

FinanceEvent covers financial changes only. **Same-price Mark/contact/destination/member changes still change logistics versions; they do not promise a FinanceEvent.** Task 4 notification/release snapshots must bind all actual receipt/ticket/document/shipment/master versions and membership IDs they depend on, and compare them again before copy/execute. A logistics version change is enough to supersede an unexecuted dependent instruction even when finance total is unchanged. Actual pickup must use Task 4's independent physical-release ledger; current `actual_release_at: null` means Task 3 has not created such a fact, not an authoritative future replacement for that ledger. No phone/Mark grouping grants customer identity or global cross-party access.
