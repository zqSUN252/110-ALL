# 本机运行与交付

正常入口为 `http://127.0.0.1:8011`，使用受控 `private/supplied-snapshot-runtime.json`。先显示欢迎页，再由人员登录。这里是用户提供包内快照的回填结果，不能称为当前生产库；真实资料、凭据和业务备份均不包含在源码ZIP里。

## 安装和启动

需要 Python 3.13、Node 22.14、PostgreSQL。此次实际验证使用独立PG17，不修改系统已有PG服务、旧110、WAHA或Docker。后端依赖锁在 `backend/requirements.lock`，前端锁在 `web/package-lock.json`。新机器按自己的受控数据库配置文件设置 `MCSTAR_CONFIG`，其中数据库连接和私有对象目录由部署人员填写，不复制源码中的默认密码。`backend/app/settings.py`列出全部配置字段，所有外部动作开关默认关闭。

配置文件使用UTF-8无BOM的JSON，放在受控且被Git忽略的目录；不要把配置值放到命令行、README或普通日志。数据库/schema需要部署人员预先创建并明确授权，`setup.ps1`只安装依赖和构建，不接管系统数据库服务。

这次新目录重建仍在同一Windows主机进行，使用主机已安装的Ebrima常规/粗体、微软雅黑及可用emoji字体；这些系统字体没有复制进ZIP。其他主机须通过`document_font_regular`、`document_font_bold`、`document_font_chinese`配置真实可用且含所需字形的字体。缺资源时正式单证明确拒绝生成，不能把本机成功推定为所有操作系统无需配置即可同版渲染。

```powershell
& tools/setup.ps1 -Python python
$env:MCSTAR_CONFIG = (Resolve-Path private/supplied-snapshot-runtime.json).Path
$env:PYTHONPATH = 'backend'
.venv/Scripts/python.exe -m app.cli init-db
& tools/start.ps1 -Background
```

`init-db`只执行版本迁移；正常交付使用已回填的数据，不自动导入测试样例。全新空环境的初始管理员由受控终端执行 `python -m app.cli create-admin --username <自选名称>`，交互输入至少12位密码；已有管理员时该命令拒绝覆盖。恢复后的原生账号通过 `tools/restore_access.py`受控重置，仍不激活旧导入账号或取消恢复写栅栏。

不加`-Background`时服务随当前终端运行；后台模式隐藏启动窗口，记录准确PID、端口和profile路径到受控 `private/processes/<启动时间>/receipt.json`。它不会注册Windows服务或开机启动。默认只监听127.0.0.1且禁用普通访问日志；外部HTTPS、域名、反向代理和系统服务部署未在本轮验收。

本地worker仅处理单证/库存导出、助手文件、备份迁移任务；不会启动模型调用、采集、配对或发送。密码哈希没有为性能测试降级。私有目录启动时逐项检查和落实ACL；大运行目录可能超过旧30秒窗口，启动脚本现在最多等待180秒，可显式设置`-StartupTimeoutSeconds`。失败必须查受控错误日志，不能把命令返回或进程存在当作健康证据。

## 保存、恢复与核对

```powershell
.venv/Scripts/python.exe tools/backup.py backup --path <受控新备份目录>
.venv/Scripts/python.exe tools/backup.py restore --path <受控备份目录> --schema restore_<自选隔离名称>
```

恢复只允许自有隔离空schema，保留FK检查及原来源数据，逐表行数/hash与附件字节核对。恢复会停用旧会话/凭据、暂停连接和发送，并设置writer_frozen；有新业务事实时必须走checkpoint/回退计划及人工核对，不能直接覆盖工作库或删除栅栏。原格式format1兼容，流式实现仍需保存随数据增长的checkpoint/fact元数据。

实际回填在g11000600002保留439条来源客户、28份出运单、964行票件、619张账单。原资料缺口、来源关联异常和未知日期在“来源记录”及对应业务详情可见。已有原生桥接共享财务身份；同号多行不会被当成重复删除。旧f6恢复证据保留，新g2备份和独立恢复另存。

## 交付包和复建

`tools/package.py`从明确公开目录和已构建的`web/dist`制作ZIP，写入逐文件SHA256清单并测试ZIP完整性及路径。排除`.git`、私有资料/配置/密钥、原始提示词、真实业务附件、`.venv`、`node_modules`及临时审查文件。业务备份另放受控私有位置，不能与源码ZIP合包。

解压到全新的自有验证目录后，使用ZIP中的`tools/setup.ps1`重新创建venv、安装锁依赖并重建前端；再用独立配置/schema启动和恢复验证。不能把原checkout成功或ZIP目录存在当成复建通过。具体交付文件hash、验证目录和结果以最终脱敏收据为准。

准确ZIP旁的 `MCSTAR-110-ALL-validation.json` 是独立验证收据，以`package_sha256`绑定该文件，包含新目录安装/构建、108表恢复和权限/写栅栏结果；不要把其他候选包的结果套到新ZIP上。源码内不嵌入自身ZIP的循环hash。重复验证可用 `tools/validate_package.py --port <空闲端口>`；启动脚本遇到占用端口会拒绝，不终止或替换已有进程。

fix1修复交付另附`MCSTAR-110-ALL-fix1-validation.json`，以它的准确ZIP hash/commit为准；原d26 ZIP与原收据保留为superseded历史版本，不覆盖改名冒充新包。新的包验证仍在独立新目录重建环境、前端及隔离恢复，实际默认入口的数据不被替换为恢复库或演示库。

## 本地检查边界

后台测试真实使用PostgreSQL，浏览器检查使用真实FastAPI与已构建React；只在隔离schema生成合成记录。客户验证码的成功链仅替换最窄的外部HTTP传输，仍执行真实挑战、哈希校验、会话、本人范围与导出，真实短信/WhatsApp通道仍未验收。完整业务浏览器链和HTTP链是两个不同证据，不能互相冒充。

缺失原宣传图、精确模板截图、当前生产备份、真实模型OCR准确率、配对/投递、微信或WhatsApp实际粘贴、物理打印和正式HTTPS均保留未验收状态。完整146项实现/测试入口/外部缺口见`docs/acceptance/实现与证据.json`。
